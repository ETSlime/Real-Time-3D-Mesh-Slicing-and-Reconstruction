Mesh Cut 日文文件名测试模型

一、文件
01_立方体.obj / .mtl：立方体，基础平切、斜切、连续切割。
02_正四面体.obj / .mtl：四面体，少面数基础测试。
03_正八面体.obj / .mtl：八面体，尖角与对称截面。
04_L字柱体.obj / .mtl：L 字棱柱，简单凹截面耳切。
05_複数材質立方体.obj / .mtl：多材质立方体，跨材质完整轮廓。
06_ドーナツ.obj / .mtl：甜甜圈，含孔截面的限制，以及不含孔切法的对照。

前五个保持原测试模型的几何、法线、UV 与材质，只改变外部文件名并同步 mtllib。
所有模型都已三角化，提供 UV 和法线；材质无需贴图。将每对 OBJ/MTL 保持在同一目录。

二、日文路径的编码条件
当前方案保留学校加载器的窄字符路径，并将拖放的宽字符路径转换为 Windows ANSI 代码页，
不属于完整 Unicode 路径导入。日文 Windows 的传统 ANSI 代码页通常为 932（CP932）。
其他代码页不能保证表示日文；系统语言、显示语言和 ANSI 代码页不能简单视为同一回事。

本包的 OBJ 和 MTL 内容使用 CP932（无 BOM）；ZIP 文件名使用 Unicode。
这样 mtllib 内的日文文件名与日文 ANSI 加载器的编码一致。
README_CN.txt 使用 UTF-8，与模型读取无关。

建议先解压到简短的 ASCII 父目录，例如 C:/MeshCutTests，再拖入日文名 OBJ。
先用 01_立方体.obj 确认路径与材质加载，再试其他模型。
不要只改 MTL 的外部文件名，也不要将 OBJ 随手另存为 UTF-8，否则内部日文引用可能失配。
若系统 ANSI 代码页为 UTF-8（65001），则本包模型文本也需要转成 UTF-8；
若为不能表示这些日文名的代码页，请先使用原来的英文名模型，不要将加载失败误认为切割错误。
本包没有在你的 Windows 上验证日文路径；CPU 几何测试不等于 Windows 文件导入测试。

三、甜甜圈的切法
环位于 XZ 平面，中心轴为 Y；大半径 5，管半径 1.75。
768 个几何顶点、1,536 个三角形，展开后 4,608 个绘制顶点。

限制用例：切割平面 y=0（穿过管体中部，并平行于环的平面）。
截面为外环包围内环，必须保留中间孔洞。当前算法预期返回 UnsupportedHole，保留原模型。
这表示暂不支持带孔的嵌套截面，不是甜甜圈模型本身不合法。

对照用例：切割平面 x=0（平面包含中心轴）。
截面为两个不嵌套的独立闭环，当前算法可以切开。
因此不是任意方向切甜甜圈都会失败。

鼠标交互：先调整相机，从甜甜圈侧面观察，让刀面接近平行于环的 XZ 平面，
并穿过管体内部；拖动范围要覆盖整个切口。数学上的精确 y=0 不一定能在任意相机位置下画出，
实际刀面还取决于相机位置和拖动方向。若没覆盖切口或只是相切，也可能返回 Unchanged。
可以用 F3 看刀面，F1 看网格，并用撤销或重新拖入 OBJ 恢复原始模型。
程序没有直接输入平面方程的界面；上面的方程用于说明与 CPU 算法测试。

四、已完成的验证
全部六个 OBJ：三角面格式、顶点/UV/法线索引、MTL 文件引用、材质名、
每条几何边恰好由两面共享、相邻绕序一致、正体积及面法线方向检查通过。
使用交付的 MeshCutter 源码进行 CPU 测试（DirectX 类型使用测试替身）：
甜甜圈 y=0 → UnsupportedHole；x=0 → Cut，生成两个闭合碎块，绕序与体积检查通过。
Windows 拖放、日文代码页、MTL 加载和渲染仍需本地验证。
